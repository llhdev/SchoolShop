# Architecture deep-dive — images, checkout, payment verification

Detail moved out of the root `AGENTS.md` to keep it under the size limit. The root file carries the map (state, navigation, data model); this file carries the reference detail. When this doc and the code disagree, the code wins.

---

## Images

- `assets/logo.png` is the web-optimized 192×192 header logo (~35 kB); the 1024×1024 source is `assets/icon.png`. Don't swap in a large logo — it ships in the first page load.
- Product images render through `ProductImage` (`expo-image`, memory + disk cache); missing images render a local placeholder (category color + product initial) — no external service, works offline.
- Uploads are resized to max 800px, stored in the Cloudflare R2 bucket `timor-shop-images` (served from `https://img.timor.et`, keys namespaced `products/` / `logos/` / `qrs/`) with a 400px `-thumb.jpg` companion (1-year `Cache-Control`). Clients never see R2 credentials: the `r2-upload-sign` edge function (secrets in setup step 9 of `docs/supabase-setup.md`) returns presigned PUT URLs after checking the caller's capabilities (052: `staff_shop` for `products/`/`books/` keys, shop owner for `logos/`/`qrs/`, `staff_financial` or `staff_branch` for proof GETs, super admin for all); the client uploads bytes straight to R2, then HEAD-verifies the public URL before returning it (a PUT that doesn't persist must fail the upload, not store a dead URL). Only the full URL is stored on the product; list views request the derived thumbnail. `scripts/migrate-images-to-r2.js` copied legacy Supabase objects and rewrote DB URLs.
- Both R2 buckets carry a CORS policy (`scripts/r2-cors.json`: origins `https://shop.timor.et` + localhost dev ports, GET/PUT/HEAD, any headers) — without it browsers block the presigned PUT at preflight and all web uploads fail (native is unaffected). Bucket creation and CORS changes are done in the Cloudflare dashboard (the token is object-scoped).
- Payment proofs live in the **private R2 bucket** `timor-shop-proofs` (no public access), stored on the order as bare object paths (keys unchanged since migration 040 — only the backend moved; `scripts/migrate-proofs-to-r2.js`). All access is presigned via `r2-upload-sign` (`_shared/r2Sign.ts`): shoppers upload with the anonymous `sign-proof-upload` action (max 4 keys, 10-min PUT URLs); admins view with `sign-proof-get` (admin-authed GET presign, falls back to the legacy `payment-proofs-private` Supabase bucket for unmigrated objects — as do `verify-order-payment`, `verify-payment-reference`, `telegram-order-notify`); proofs are not shown to shoppers. Bank QR codes were in `bank-qrs` (020) — now `qrs/` in R2, uploaded as-is (no resize — QRs must stay scannable), never auto-deleted.
- Cover thumbnails are prefetched when the catalog loads. `coverImageIndex` picks the card/list image.
- `utils/images.ts`: `getProductCoverImage`, `getProductGalleryImages`, `getThumbnailUrl`; `services/images.ts`: upload/delete/URL parsing.
- On web, native image modules don't run: `src/lib/image-web.ts` uses a hidden `<input type="file">` + canvas. Native-only modules are **dynamically imported** everywhere so they stay out of the web bundle.

## Checkout behavior

- Checkout collects, in order: optional delivery `location`, Ethiopian phone (required, validated by `isValidEthiopianPhoneNumber`), per-product **checkout questions** (036 — answers snapshotted onto the item's `fieldAnswers`; a tenant who needs a name adds a "Name" question — there is no fixed student-name field), then per-shop payment proof. A landmark picker (`src/constants/landmarks.ts`) fills the location.
- Only payment method: **direct bank transfer**. Checkout groups the cart by tenant and shows per shop: name, bank accounts (number + bank + QR, via `fetch_products_with_shop`), subtotal + flat shipping fee. The shopper uploads **one proof photo per shop** (`uploadPaymentProof`, 800px); every shop needs a proof before ordering.
- **Pre-order verification (041).** After each proof upload, the transaction reference is read off the receipt — web/TMA via **Tesseract.js OCR** (`src/lib/ocr.ts`, lazy CDN worker, runs on the full-resolution original — the 800px proof copy garbles small text; CBE Receipt ID / Telebirr transaction numbers only), elsewhere typed manually (when the receipt prints no brand name, the extractor falls back to provider label vocabulary plus the shopper's "Paid via" hint) — and checked by `verify-payment-reference` (`verify_jwt = false`; handles CORS/OPTIONS itself — every browser-called edge function must; curl/Node tests never catch a missing preflight; gated by proof existence in the private bucket + daily precheck cap + idempotency-key replay in `payment_prechecks`). It recomputes the expected amount server-side (`_shared/variantPricing.ts`), syncs the tenant's verify.et registry (`_shared/verifyRegistry.ts`), and calls verify.et's **reference JSON API** (no image credits; legacy CBE `FT…` references additionally send the receiver account's 8-digit `suffix` — `_shared/referenceSuffix.ts`, modern Receipt IDs must not). Masked receivers (`1****8566`, `2519****1630`) are matched to the shop's own accounts by visible digits (`matchMaskedAccounts` in `_shared/verifyEvaluation.ts`) — unique match passes, different account is `wrong_recipient`, ambiguous stays review. Every response carries a `detail` reason (verify.et's error or the failed/reviewed check reasons), shown in checkout under the friendly message. Verdicts: `verified` / `not_found` (fix and retry) / `wrong_recipient` / `wrong_amount` / `already_claimed` (hard rejects — new proof required) / `unavailable` (temporary, retryable — never an invalid payment). **Place Order is gated on every shop reaching `verified`**; the `{ provider, reference, key }` per tenant lands on `orders.payment_references`.
- Orders start `pending` with proofs on `orders.payment_proofs`. `telegram-order-notify` sends each tenant their order summary **plus their proof photo** (product image URLs are HEAD-checked first — a dead one is skipped so it can't sink the whole album, proof included); each item's checkout answers are listed under it. Run `node scripts/check-product-images.js` to audit every product image URL for 404s.
- **Order-time verification (040–041).** An AFTER INSERT orders trigger calls `verify-order-payment` (client never triggers it). Orders with `payment_references` replay the pre-order check with the **same idempotency key** (free on verify.et's side — the JSON body must stay identical, `{ bank, reference }` plus the CBE suffix when applicable); legacy orders fall back to image-based submission. Each proof is checked for completion, exact recipient account, exact amount (items + fee), prior claim (`payment_claims`), and receipt age (`RECEIPT_MAX_AGE_HOURS`, default 24). Attempts log in `payment_verifications` (`is_current` = active); queued ones complete via the signed `verify-et-webhook`. Retry/approve (`retry_payment_verification` / `approve_payment_verification`, on OrderDetail and in `AdminUserOrdersScreen`) require the **Financial capability** since 052 (super admin always; the owner needs its financial toggle on). Verification never changes order status — approval stays manual.
- **Runtime kill-switch (042) + per-tenant switch (043).** `platform_settings.payment_verification_enabled` (public read, super-admin write) gates the whole pipeline, and `profiles.payment_verification_enabled` excludes individual shops — a shop is verified only when BOTH are on. All three edge functions read the flags per request (missing/error = disabled, fail-safe). Flip them from Tenant Management (global switch at the top, per-shop switch on each tenant card) or with SQL: `UPDATE platform_settings SET value = 'false' WHERE key = 'payment_verification_enabled';` / `UPDATE profiles SET payment_verification_enabled = false WHERE id = '<tenant>';`. While off for a shop: checkout skips its verification (proof alone suffices, pre-040 behavior), the pre-check returns `{"skipped":"verification disabled"}` (client maps it to `unavailable`), order-time verification skips that shop's slice, and the webhook acks without touching verify.et or Telegram. `telegram-order-notify` is unaffected.
- Tenant bank details live on `profiles.bank_accounts`, the fee on `profiles.shipping_fee`: super admin sets them at tenant creation/edit; tenants maintain their own via `update_own_bank_accounts` / `update_own_shipping_fee` in Account & Security. Each fee is charged once per order, added to that shop's transfer amount, stored on `orders.shipping_fees`, included in `orders.total`.
  Merchant account editing is temporarily disabled for STAFF accounts: `MERCHANT_ACCOUNT_EDITING_ENABLED = false` in `src/constants/featureFlags.ts` hides staff Account & Security editing (password, shop description, Telegram username, bank details, shipping fee incl. its Add/Edit Item field) and entry points; flip to `true` to re-enable. The shop owner (048) and super admin are unaffected.
- A checkout creates a single `Order` containing all cart line items, sharing one location and phone number.
