# Security considerations

Moved out of the root `AGENTS.md`. When this doc and the code disagree, the code wins.

- **Admin authentication.** Supabase Auth. Roles: `super_admin` (full) and `admin` (tenant; edits only own products). `get_admin_by_username` returns data only for an exact match.
  Credential management (013/048): admins change own username/password in Account & Security; super admin edits tenant credentials via SECURITY DEFINER RPCs. A guard trigger blocks non-super-admins from changing any profile's `role`/`email` — and since 048 also the staff columns (`parent_tenant_id`, `staff_*`, `branch_id`, `staff_label`), which only the super admin or the owning shop owner may touch.
  Tenant codes (014): every profile gets a short `XXXX-XXXX` code from `fill_tenant_code` — the auth UUID is never shown in the UI. Tenant creation accepts an optional custom email (blank derives `<username>@tenant.schoolshop.app`); since 058 the signup trigger always creates `role='user'` (client-controlled signup metadata never grants roles) and Tenant Management promotes the account via the super-admin-only `admin_promote_to_tenant` RPC.
  `SUPABASE_ADMIN_EMAIL`/`SUPABASE_ADMIN_PASSWORD` must NOT use the `EXPO_PUBLIC_` prefix — that inlines values into the client bundle. Self-signup always yields `role='user'` (058), so knowing the tenant email pattern no longer grants admin; privileged EXECUTE grants (`verify_function_secret`, `request_payment_verification`, `delete_tenant_user`) are revoked from anon (058), and anonymous storage DELETE policies on `payment-proofs`/`bank-qrs`/`shop-logos` plus the any-authenticated read on `payment-proofs-private` are dropped (058), and the anonymous UPLOAD policies on those legacy buckets plus the public read on `payment-proofs` are dropped too (060). The `shoppers` table is read-only for clients (059 — writes go through `telegram-auth` only).
- **Scoped reads, authenticated writes.** Products/categories publicly readable; orders placed without auth. Order SELECT is NOT public anymore (062–065): guests re-fetch their own orders via `get_order_for_shopper(order_id, phone)` (phone is required at checkout since 063, so the id+phone pair is the capability), Mini App history goes through `get_orders_by_telegram_id` with an HMAC token issued by `telegram-auth` (062), and staff reads are capability-scoped — direct table SELECT needs the Financial capability (064), everyone else gets money-stripped rows from `get_scoped_orders` (and no realtime). Order writes are locked down (052): UPDATE/DELETE are super-admin-only — tenants move statuses exclusively through the capability-gated `update_order_item_status` RPC, and `retry`/`approve_payment_verification` require the Financial capability. The insert trigger recomputes all money server-side (variant prices, shipping fees, total), requires a phone number, wipes `telegram_notifications`/`item_statuses`, and gates `payment_references`/`payment_warnings` on `payment_prechecks` rows (063). Payment-proof reads via `r2-upload-sign` are limited to financial/branch staff of an active shop; image/PDF uploads require the Shop capability; logo/QR keys are owner-only; all keys are tenant-namespaced (061) and anonymous proof uploads are rate-limited per IP (061).
- **Payment verification trust boundary (040–042).** Orders are inserted by anonymous clients, so nothing on the order is trusted: `verify-order-payment` recomputes the expected amount from the catalog (`_shared/variantPricing.ts` + `profiles.shipping_fee`), `created_at` is forced to `now()` by trigger (041), and the atomic claim (`payment_claims` PK on `(provider, reference)`, ON CONFLICT read-back) fails closed on DB errors. Concurrent orders for one reference: exactly one claim wins; the loser fails `notPreviouslyClaimed`.
- **Local cache.** AsyncStorage is unencrypted. Never store real payment data, passwords, or PII.
- **Telegram shopper identity.** `telegram-auth` validates Telegram's signed initData (timing-safe compare; initData older than 24 h is rejected as replay protection), so the shopper record is trustworthy. Orders carry a client-supplied `telegram_id` under public-insert RLS, but reading history requires the HMAC token (062) and `attach_order_telegram_id` requires the order's phone — a forged telegram_id no longer leaks another user's orders.
  initData HMAC gotcha: `secret_key = HMAC(key="WebAppData", message=bot_token)` — swapping key/message silently rejects every real initData. If the SDK script fails (slow networks), `initTelegram()` falls back to a stub WebApp from the `tgWebAppData` URL parameter (callers check `hasTelegramChrome()`).
- Storage objects are not auto-deleted when a product is removed (best-effort deletion).
